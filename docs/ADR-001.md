# ADR-001: Extract existing blocks while retaining inherited representation

## Context

Inherited top-level code mixes file access, tuple preparation, two calculations,
printing/plotting and execution. We must work with this application, preserve its
functionality/history, and satisfy the activity's distinct responsibilities and multiple
meaningful modules. The selected approach uses small, traceable source extractions.

## Alternatives

1. Add comparison directly to the original script: minimal initial effort, but does not
   satisfy AR1/AR2 and leaves analysis coupled to import-time I/O.
2. Extract the existing blocks into focused functions/modules with tuples unchanged:
   selected; meets modularity through direct movement of inherited statements.
3. Introduce record classes, new CLI architecture or stricter preparation validation:
   unnecessary for this requirement and would obscure the original-to-refactored mapping.
4. Generic framework or distributed services: adds indirection/operational cost without need.

## Decision

Keep evacodev2.py as the coordinator. Extract reading, preparation, calculations and
presentation. Keep the tuple shape, original conversion/sorting/accumulation/sum and
pyplot calls. Use arguments/returns in place of shared globals and guard execution.

## Rationale

Boundaries follow responsibilities. Known-answer tests can call calculations using
in-memory tuples without opening files, prompting or importing Matplotlib. Original
operations remain identifiable; no new domain abstraction is necessary.

## Consequences

More files and positional contracts to document, but local responsibilities and explicit
interfaces. Tuple changes would still affect callers. Testability/analysability improve
structurally; no claim of measured developer speedup. Source provenance and exact
baseline tests will support preservation rather than relying only on matching totals.
